AIに依存しない、設計の資産——Mothership

2026.06 Figma Plugin Claude Code Published

Mothership は、設計の原本(JSON)を編集可能な本物のFigmaノードへ翻訳するFigmaプラグインだ。「AIでFigmaを操作する道具」ではない。目指したのは、デザインをAIに依存しない資産として蓄積し、人とAIが共同編集できる環境。2026年6月、Figma Community に公開した。この記録は、その設計判断の覚え書きである。

出発点：「AIがFigmaを操作する」ことへの違和感

生成AIでデザインを作る流れは速くなった。けれど多くは、AIがツールを直接動かし、出てきた結果を受け取る形になっている。これだと、資産はAIとの接続方法に縛られ、モデルやサービスが変われば足元から崩れる。デザイナーが本当に残したいのは、画像でも生成ログでもなく、設計そのもののはずだ。Mothershipは「AIに操作させる」のではなく、「設計を原本として持ち、AIにはそれを翻訳させる」方向から組み直した。

設計の核心：中心に置くのは、AIではなく原本のJSON

Mothershipの中心には、ひとつの mothership.json がある。レイアウト・コンポーネント・情報構造・タイポグラフィ・デザインルールを、すべてこの一枚に持つ。Claude Code が"コードを書くのと同じやり方"でこれを編集し、プラグインがFigmaへネイティブに建てる。保存されるのは画像ではなく、設計情報そのもの。だからAIが何であっても、資産は残る。

一般的な構成： AI → MCP → Figma　（資産がAI接続に依存）
Mothership： AI → Mothership JSON → Figma → 資産化　（中心はJSON）

なぜMCPを採用しなかったのか

MCPは優れた技術だ。Mothershipが中心に据えなかったのは、MCPが悪いからではなく、実現したい未来が違うから。理由は四つ。①AIを交換可能に——中心がJSONなら、Claude も ChatGPT も Gemini も、これから生まれるAIも使える。②資産を永続化——モデルは消え、サービスは終わる。それでも設計は残らなければならない。③Figmaを中心に——「AIがFigmaを操作する」のではなく「Figmaが最終成果物になる」。④導入障壁を下げる——MCPサーバー構築や環境設定は、技術者には平気でも、デザイナーには壁になる。大事なのは技術の新しさではなく、誰でも使えることだ。

ゼロセットアップで動く、という設計判断

「誰でも使える」は、最初の一歩で決まる。Mothershipはプラグインを開いてすぐ、セットアップなしでサンプルを生成できるボタンを置いた。relayもアカウントも通信も要らず、押せば本物のFigmaレイヤーが建つ。ここで「これは本当に編集できるノードだ」と体感してから、必要な人だけがライブモード（Claude Code連携）へ進む。導入の摩擦を、最初の一クリックで溶かす設計だ。

詰めの精度こそが、堀

プロが値踏みするのは、タイポの精度・余白・プロポーションだ。そこが甘ければ、手で描いた方が早い＝使われない。だからMothershipは、写真や派手さではなく"詰めの精度"に価値を置く。参照画像を重ねて数値で詰めるビューで、最後の一押しを引き受ける。そして詰め切ったパターンはライブラリに貯まり、次が速くなる。使うほど鋭くなる、終わらないループ——それがこの製品の堀だ。

判断するのは人。蓄積されるのは知識。
継承されるのは、設計思想。

今日のMothershipは「チャットからFigmaを生成するツール」に見えるかもしれない。けれど本当に目指すのは、個人や組織のデザイン知識を蓄積し、再利用し、育て続けられる環境だ。AIは、そのための翻訳者に過ぎない。
